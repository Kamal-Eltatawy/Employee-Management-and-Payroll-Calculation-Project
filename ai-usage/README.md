# AI Usage

This folder contains the AI chat sessions used to build this project, plus notes on how AI was used. The desktop app offers no usable export, so each session was reconstructed by the assistant at the end of the session: Kamal's messages translated from Egyptian Arabic into English, the assistant's replies condensed, and personal remarks unrelated to the project left out and marked (see the note at the top of each file).

## How the work was split

**Generated by AI (and reviewed by me):**

- All production code: Domain, Application, Infrastructure, Api and the Angular client.
- All tests: xUnit unit tests (Domain, Application, Api), the Testcontainers integration tests and the Angular logic tests.
- The design spec, the master plan, `PROGRESS.md` and this documentation, including `README.md`.

**Done by me:**

- Every decision. Each open point was asked as one question with options and a recommendation, and I chose (decision log D1–D71 in the spec).
- Changes in direction during implementation that came from my own review: tax schemes per employee with pluggable tax methods (D53), keeping the current month open so a policy mistake can be corrected before payroll (D54), rotating refresh tokens (D55), after a full review, multi-role users, account lockout and the other review items (D65–D69), and HR screens for pay items and policies with an editable kind while an item is unused (D70–D71).
- Running every build, test, migration and container; reporting the output; and testing the UI and Swagger by hand. Problems found this way and then fixed: a vulnerable transitive package (NuGet audit), a C# target-typed `new()` error, a port clash with a local SQL Server, model-binding errors not matching the Problem Details shape, the network-error toast message, and Swagger UI answering 401 under the fallback authorization policy.
- All Git operations. The AI never committed or pushed (D50).

## Author's note: working across several sessions

The design discussion in session 1 was deliberately long. Every architectural decision was asked as a single question with options, and each decision was recorded in the spec's decision log. By the end of Phase 1 the conversation context had grown very large, so every new message was consuming a lot of tokens.

I decided to continue the implementation in **new sessions** and to switch to a leaner working mode (decision **D52** in `docs/design/2026-11-09-employee-payroll-design.md`):

- one batch of code and tests per phase;
- one build and test run per phase;
- no further per-phase detailed plans;
- the agreed scope stays unchanged.

Continuity between sessions is handled by two files:

- `CLAUDE.md` holds the standing rules and is read automatically at the start of every session.
- `docs/plans/PROGRESS.md` records the exact current state and the next action.
